# C3P 통합 수행 규칙 — 단일 계획, 프로젝트 대화창 및 순차 스케줄

## 결정

**MIA Decision Gate: Go.** C3P 협의체 (C3P Council, Codex·Claude Code·Antigravity가 함께 검토하고 실행하는 3도구 협업 체계)의 모든 후속 저장소 작업은 이 문서를 단일 정본 계획으로 사용한다. 각 도구가 독립 계획을 세워 동시에 구현하는 방식을 중단하고, 하나의 작업 ID·하나의 승인된 작업 카드·하나의 순차 상태머신으로 실행한다.

이 규칙은 사용자 제안을 프로젝트 수행 규칙으로 고정한 것이다.

1. 저장소 작업은 일반 사용자 대화창이나 프로젝트 밖 임시 대화에서 수행하지 않는다.
2. 각 수행 작업마다 각 도구의 **해당 프로젝트 안에 전용 대화창을 하나씩** 만든다.
3. 세 대화창은 동일한 작업 ID와 제목을 공유하고 역할 접두어만 구분한다.
4. 구현 쓰기 권한은 한 시점에 한 도구만 가진다.
5. 다음 단계는 이전 단계의 증거와 인계 카드가 확인된 뒤 시작한다.

`docs/23`의 계획·상태 변경 권한은 **Codex 계획 대화창**에만 있다. Claude Code와 Antigravity는 변경 제안을 인계 카드로 반환하며 이 문서를 직접 수정하지 않는다. 사용자가 직접 수정하거나 명시적으로 다른 도구에 권한을 부여한 경우만 예외다.

## 통일 대화창 접두어

### 제목 규격

```text
[C3P][Wnn][ROLE] 작업명
```

* `Wnn`: 두 자리 작업 ID. 예: `W01`, `W02`.
* `ROLE`:
  * `PLAN` — Codex 기획·통합·종결
  * `BUILD` — Claude Code 구현·단위/실패경로 테스트
  * `VERIFY` — Antigravity 독립 검증·E2E·사용자 관측
* 작업명은 세 도구에서 완전히 동일하게 사용한다.

예시:

```text
[C3P][W01][PLAN] 결과 의미론과 위장 성공 제거
[C3P][W01][BUILD] 결과 의미론과 위장 성공 제거
[C3P][W01][VERIFY] 결과 의미론과 위장 성공 제거
```

대화창 상태는 제목을 반복 변경하지 않고 각 대화의 최신 상태 카드에 기록한다.

### 프로젝트 창 원칙

* Codex: 이 저장소로 저장된 프로젝트 안에 새 작업을 생성한다.
* Claude Code: 이 저장소 경로에 귀속된 프로젝트 세션을 생성하고 위 제목으로 명명한다.
* Antigravity: 이 저장소의 프로젝트 ID에 귀속된 대화를 생성하고 위 제목을 사용한다.
* 프로젝트 UI가 없는 실행 경로라면 정확한 저장소 경로·작업 ID·제목을 가진 영속 세션으로 대체한다.
* 한 대화창에서 서로 다른 `Wnn` 작업을 섞지 않는다.
* 같은 도구·같은 작업 ID의 대화창을 중복 생성하지 않는다. 이미 있으면 해당 대화를 이어간다.

## 통합 작업 상태머신

```text
DRAFT → PLAN_LOCKED → BUILDING → BUILT → VERIFYING → VERIFIED → CLOSED
                    ↘ BLOCKED / NEEDS_REVIEW ↗
```

| 상태 | 주책임 | 허용 작업 | 다음 상태 조건 |
|---|---|---|---|
| `DRAFT` | Codex | 현황·제약·대안 정리 | 사용자 또는 기존 합의로 범위 확정 |
| `PLAN_LOCKED` | Codex | 작업 카드 발행 | 대상 파일·완료기준·금지사항·기준 SHA 확정 |
| `BUILDING` | Claude Code | 승인 범위 구현 | 관련 테스트와 diff 증거 생성 |
| `BUILT` | Claude Code | 인계 카드 작성 | 변경 파일·검증 결과·잔여 위험 명시 |
| `VERIFYING` | Antigravity | 독립 검사·E2E | 구현 변경 없이 검증 증거 생성 |
| `VERIFIED` | Antigravity | 검증 인계 | 완료기준 전부 충족 또는 실패 명시 |
| `CLOSED` | Codex | 종합 판정·정본 상태 갱신 | 증거 대조와 사용자 승인 경계 확인 |
| `BLOCKED` | 해당 단계 책임자 | 원인·대안 보고 | 새 권한·입력·환경 변화 확보 |
| `NEEDS_REVIEW` | Codex/사용자 | 충돌·미지 상태 판정 | 범위 재고정 |

`PLAN_LOCKED` 이전 구현, `BUILT` 이전 검증, `VERIFIED` 이전 완료 선언은 금지한다.

## 도구별 고정 역할

### Codex — PLAN 및 통제면

* 저장소 기준선, 기존 변경 소유권, 사용자 목표를 확인한다.
* 하나의 작업 카드와 완료기준을 확정한다.
* Claude·Antigravity의 인계를 비교하고 합의·충돌·UNKNOWN을 판정한다.
* 다른 도구가 구현 중인 파일을 수정하지 않는다.

### Claude Code — BUILD

* `PLAN_LOCKED` 작업 카드 범위만 구현한다.
* 계획이나 파일 범위를 임의 확장하지 않는다.
* 실패 테스트 → 최소 수정 → 회귀 검증 순서를 지킨다.
* 완료 후 `BUILT` 인계 카드를 반환하고 쓰기를 멈춘다.

### Antigravity — VERIFY

* `BUILT` 인계를 받은 뒤 실제 사용자 관측·통합·E2E 경로를 독립 검증한다.
* 검증 단계에서 구현 코드를 자동 교정하지 않는다.
* 실패하면 재현 증거와 분류를 반환하고 상태를 `NEEDS_REVIEW`로 둔다.
* 구현 변경이 필요하면 새 작업 카드가 발행될 때까지 기다린다.

## 표준 작업 카드

모든 대화창의 첫 메시지와 각 단계 인계는 아래 형식을 사용한다.

```yaml
work_id: Wnn
title: 동일한 작업명
state: PLAN_LOCKED | BUILT | VERIFIED | BLOCKED | NEEDS_REVIEW
owner: codex | claude_code | antigravity
source_plan: docs/23 + docs/22
base_revision: commit SHA 또는 WORKING_TREE_SNAPSHOT
goal: 한 문장 목표
scope:
  files: [허용 파일]
  actions: [허용 행위]
non_goals: [금지 범위]
acceptance:
  - 검증 가능한 완료기준
evidence:
  tests: [명령과 exit code]
  artifacts: [diff/로그/스크린샷 해시 또는 경로]
risks: [잔여 위험]
next_owner: codex | claude_code | antigravity | user
```

필수 필드가 빠지면 다음 도구는 실행하지 않고 `BLOCKED_CARD_INCOMPLETE`를 반환한다.

## 동시성·소유권 규칙

1. 같은 `Wnn`에서 쓰기 토큰은 하나뿐이다. 기본 순서는 `Codex 계획 → Claude 구현 → Antigravity 검증 → Codex 종결`이다.
2. Claude가 `BUILDING`이면 Codex와 Antigravity는 대상 파일을 읽기만 한다.
3. Antigravity가 검증 중 발견한 수정사항은 코드에 직접 적용하지 않고 새 결함 카드로 반환한다.
4. 이미 존재하는 미커밋 변경은 작성 도구가 명시적으로 인계하기 전까지 타 도구 소유로 간주한다.
5. 공유 인터페이스·스키마·잠금·상태머신 파일은 작업 범위를 분리해도 병렬 수정하지 않는다.
6. 테스트·문서 번호·계획 상태처럼 공유 상태를 바꾸는 작업은 직렬화한다.
7. 작업이 막혀도 다른 계획을 임의로 시작하지 않는다. Codex가 새 `Wnn`을 발행해야 한다.

## 완료·중단 규칙

* 테스트 수만 늘어난 것은 완료가 아니다. 해당 작업의 acceptance와 실패경로 증거가 필요하다.
* 응답하지 않은 도구는 동의한 것으로 간주하지 않는다.
* `UNKNOWN`을 `SUCCESS`로 승격하지 않는다.
* 인증, 결제, 배포, 삭제, 병합, discard 등 추가 권한이 필요한 작업은 사용자 승인 경계를 지킨다.
* 같은 원인으로 세 번 실패하면 재시도를 중단하고 `BLOCKED`로 반환한다.
* 긴급 예외는 사용자가 작업 ID·범위·단독 작성자를 명시적으로 지정한 경우에만 허용한다.

## 계획 변경 절차

1. 변경 제안은 해당 작업 대화창에서 카드로 제출한다.
2. Codex가 영향·대안·소유권 충돌을 검토한다.
3. 사용자의 최신 의도와 충돌하지 않으면 `docs/23`을 갱신하고 revision을 기록한다.
4. 세 도구의 기존 대화창에 변경된 카드만 전달한다.
5. 새 계획이 잠기기 전까지 구현을 재개하지 않는다.
