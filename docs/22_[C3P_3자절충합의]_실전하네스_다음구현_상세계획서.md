# C3P 3자 절충 합의 — 실전하네스 다음 구현 상세계획서

## 결론

**Decision Gate: Pivot 후 제한적 Go.** `docs/21`의 방향은 채택하되, 현재 추가된 코드는 “실전하네스 완성”이 아니라 **Fail-Closed 락 가드와 실전 실행모드의 초안**으로 판정한다. 다음 구현은 기능 확대보다 위장 성공 제거와 실제 실행 증거 1건 확보를 먼저 수행한다.

합의된 원칙은 세 가지다.

1. 모의 실행은 허용하지만 결과를 `SUCCESS`나 `VERIFIED_GREEN`으로 표시하지 않는다.
2. 실제 `WorktreePool` 계약과 연결되기 전에는 worktree 브리지를 실행하지 않으며, 성공 산출물을 자동 폐기하거나 병합하지 않는다.
3. `3-ALIVE`는 Ollama 한 구성요소의 상태가 아니라 Codex·Claude Code·Antigravity 각각의 실제 준비상태와 증거를 모두 충족할 때만 선언한다.

## MIA Stage 1 — 3자 입장과 절충

| 참여자 | 핵심 입장 | 수용 여부 | 절충 결과 |
|---|---|---|---|
| Antigravity | Fail-Closed 락 가드, `MOCK/HYBRID/STRICT_LIVE`, liveness, worktree 브리지, 신규 테스트를 우선 구현 | 부분 수용 | 락 가드는 유지. 나머지는 실제 계약·증거가 생길 때까지 미완료 또는 차단 |
| Claude Code | 위장 녹색 제거, real WorktreePool 계약 전 브리지 차단, 자동 discard 금지, 테스트 수 대신 실패 주입 증거 요구 | 수용 | P0 수용 기준에 반영 |
| Codex | 단일 실제 executor와 evidence receipt를 먼저 만들고, 이후 triage·liveness·다도구 확장 | 수용 | 최종 구현 순서의 기준 |

Claude Code는 Codex 절충안에 **동의**하되 다음 세 가지 수정을 요구했고, 이를 최종안에 반영한다.

1. worktree 브리지는 “미완료 표기”만 하지 않고 실제 계약 검증 전 `NOT_CONFIGURED`로 차단한다.
2. 고정 성공 제거 대상을 `STRICT_LIVE`뿐 아니라 `HYBRID`까지 확대한다.
3. 93개 테스트 수가 아니라 실패 주입의 Red→Green과 실제 실행 영수증을 승인 근거로 삼는다.

## MIA Stage 2 — /CRITIC

### 유지할 구현

* 락 획득 결과가 `ACQUIRED`가 아니면 Stage 3 진입 전에 `HALTED_LOCK_CONFLICT`로 종료하는 가드.
* `ExecutionMode`라는 명시적 개념.
* Ollama health probe 자체. 단, 전체 협의체 상태로 승격하지 않는다.
* index lock 관련 인프라 패턴 보강. 단, 광범위 정규식 오탐 회귀 테스트를 추가한다.

### 교정이 필요한 구현

1. **실제 WorktreePool 계약 불일치**
   * 실제: `acquire(agent_id, ref)` → `Dict`; `release(name, agent_id, discard)` → `Dict`.
   * 신규 Dummy: `acquire(holder_id, purpose)` → slot object; `release(name, discard)`.
   * 현 테스트는 실제 구현과 연결되지 않으므로 bridge 통합 증거가 아니다.

2. **성공 산출물 자동 폐기**
   * `finally`에서 `release(..., discard=True)`를 무조건 호출한다.
   * 실제 패치가 성공해도 export/evidence 생성 전에 변경을 지울 수 있다.

3. **HYBRID/STRICT_LIVE 위장 성공**
   * 비모의 경로가 실제 CLI executor를 호출하지 않고 고정 `SUCCESS`를 반환한다.
   * Stage 4도 실제 Antigravity 검증 없이 `VERIFIED_GREEN`이다.

4. **불완전한 liveness**
   * Ollama만 건강하면 `THREE_ALIVE`가 된다.
   * Codex·Claude Code·Antigravity의 인증, 세션, 쿼터, executor 준비상태는 관측하지 않는다.

5. **부분적인 triage 결합**
   * 현재 신규 결합은 worktree acquire 예외에만 적용된다.
   * 실제 executor exit, timeout, 429, 테스트 실패에는 아직 연결되지 않았다.

## MIA Stage 3 — /STEPBYSTEP 최종 구현 순서

### Step 1. 결과 의미론 교정 — P0

**목표:** 어떤 모드도 증거 없이 성공을 선언하지 않는다.

* `MOCK` 결과는 `SIMULATED`로 반환한다.
* `HYBRID`는 실제 단계와 모의 단계를 trace에서 개별 표시하고 전체 결과는 `PARTIAL/UNVERIFIED`로 제한한다.
* `STRICT_LIVE`는 executor adapter 미설정 시 `NOT_CONFIGURED`; 실행·검증 증거 누락 시 `UNVERIFIED`.
* Stage 4의 고정 `VERIFIED_GREEN`을 제거한다.

**완료 기준:** 고정 성공 문자열을 검출하는 테스트가 먼저 실패하고, 교정 후 통과한다. 실제 executor 증거가 없는 테스트에서 `overall_status == SUCCESS`는 0건이다.

### Step 2. 실제 WorktreePool 계약 브리지 — P0

**목표:** Dummy가 아니라 실제 pool의 반환 계약과 수명주기를 사용한다.

* adapter가 `Dict` 반환의 `status`, `slot`, `path`를 검증한다.
* `acquire(agent_id="claude_immune", ref=base_sha)`와 `release(name, agent_id, discard)`를 정확히 호출한다.
* patch 성공 후 `export_changes()` → patch/artifact digest → verifier 결과 저장 순서로 처리한다.
* merge와 discard는 자동 실행하지 않는다. 검증 실패는 `QUARANTINED/NEEDS_REVIEW`; 사용자 승인 후 별도 정리한다.

**완료 기준:** 실제 임시 Git 저장소와 실제 `WorktreePool`을 사용한 테스트에서 acquire → 변경 → export → release가 통과하고, export 전 discard 시도는 실패한다.

### Step 3. 단일 실제 executor PoC — P0

**목표:** Claude Code 또는 Codex 중 하나만 먼저 실제로 연결한다.

* 입력: 안정적인 `job_id`, base commit SHA, 허용 파일 범위, timeout, 명령 allowlist.
* 출력: executor 이름/버전, 시작·종료시각, exit code, stdout/stderr digest, diff digest, 변경 파일 목록.
* 질문·권한 대기·인증 실패는 성공이 아니라 별도 상태로 반환한다.

**완료 기준:** 동일 fixture를 대상으로 사람이 재현 가능한 실제 실행 영수증 1건. 재실행 시 중복 부작용이 없고, 증거 누락 시 성공 불가.

### Step 4. 실제 실패 경로에 triage 연결 — P1

**목표:** 추측 로그가 아니라 executor 결과를 분류한다.

* timeout, 429/quota, auth, process crash, test assertion, compilation error를 분리한다.
* `UNKNOWN`과 충돌 판정은 `NEEDS_REVIEW`, `code_edit_permitted=False`.
* 인프라 오류에는 코드 수정 루프를 열지 않는다.

**완료 기준:** 인프라 오류와 코드 오류 각각 최소 2개 실패 주입에서 서로 다른 경로로 수렴하고, 반대 방향 오분류 회귀 테스트를 함께 통과한다.

### Step 5. 도구별 상태와 협의체 상태 도출 — P1

**목표:** `3-ALIVE`를 계산 가능한 상태로 만든다.

* 각 도구 상태: `UNKNOWN`, `READY`, `BUSY`, `DEGRADED`, `AUTH_REQUIRED`, `QUOTA_BLOCKED`, `OFFLINE`.
* 각 상태에 `observed_at`, `evidence_type`, `expires_at`을 둔다.
* `3-ALIVE`는 Codex·Claude Code·Antigravity 모두 유효한 `READY/BUSY` 증거가 있을 때만 파생한다.
* Ollama는 보조 하네스 상태로 따로 표시한다.

**완료 기준:** Ollama만 READY일 때 `3-ALIVE`가 되지 않고, stale heartbeat·auth failure·recovery 전이가 결정론적으로 검증된다.

## 중단선과 비목표

* 이 계획은 Antigravity가 이미 만든 변경을 자동 승인하거나 병합하지 않는다.
* 현재 공유 작업트리의 변경은 Antigravity 소유로 간주하며, Codex는 겹치는 파일을 수정하지 않는다.
* 실제 executor 영수증 전에는 다중 worker, 자동 merge, 자동 rollback, 캐시 keep-alive, 비용절감률 홍보를 구현하지 않는다.
* 외부 세 도구가 직접 응답하지 않은 상태를 합의로 표현하지 않는다.

## 검증·비용 기록

* Codex 독립 재검증: **93 tests, OK, Exit 0**.
* Claude Code 지정 세션은 두 차례 최종 검토에서 절충안 동의를 반환했다.
* 이번 Claude 협의 호출의 도구 보고상 list-basis 비용 합계는 약 **$2.36**이며, 첫 재개 호출에서 1시간 캐시 203,825 입력 토큰이 새로 생성됐다. 이는 세션 재개 자체도 비용·쿼터 관측 대상이어야 함을 보여준다.
* Antigravity 신규 변경은 `docs/21`, 수정된 3개 모듈, `tests/test_live_orchestration.py`로 관측됐다. 현재 실행 결과는 93개 테스트 통과이나 위 계약 공백이 남아 있다.

## 최종 승인 게이트

다음 구현 착수 범위는 **Step 1만 우선 승인**한다. Step 1의 Red→Green 증거와 다른 세션 변경의 소유권 정리가 확인된 뒤 Step 2로 넘어간다. Step 3의 실제 실행 영수증 전에는 “실전 E2E 완성” 또는 “3-Alive”를 선언하지 않는다.
